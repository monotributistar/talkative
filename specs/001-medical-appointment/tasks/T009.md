# T009 — Ejecutor de tareas, intentos, retry y handoff

**Owner:** Execution

**Estado:** done

**Depende de:** T006, T007, T008

**Archivos permitidos:** `backend/src/execution/**`,
`specs/001-medical-appointment/tasks/T009.md`

## Objetivo

Implementar el boundary determinista que toma un `TaskCommand` ya estructurado,
valida su correspondencia con el agregado persistido, obtiene autoridad de
`ConsentManager`, crea un único `Attempt`, ejecuta el adaptador asignado y
persiste su resultado con reintentos limitados y handoff explícito.

## Contratos

- Consume:
  - `TaskCommand` y `AdapterResult` v1 congelados en T002;
  - `AppointmentAdapter` y clínica sintética de T006;
  - `CaseManager` T007 como única autoridad sobre `Case.status`;
  - `ConsentManager` T008 como única autoridad para divulgar datos.
- Produce:
  - `TaskExecutor.execute(command)`;
  - `TaskExecutionOutcome`, que incluye cuando existan el intento persistido y
    el resultado del adaptador, más una decisión determinista `completed`,
    `retry_scheduled`,
    `waiting_external`, `needs_user` o `needs_human`;
    el handoff por límite agrega `handoffReason=ATTEMPTS_EXHAUSTED` sin
    reemplazar ni perder el `AdapterResult` original;
  - errores tipados sin datos personales ni clínicos.
- No puede cambiar: contratos T002, schema Prisma, conversación, rutas,
  adaptadores T006, `CaseManager`, `ConsentManager` ni wiring global.

## Reglas congeladas

1. El comando debe coincidir exactamente con tenant, caso, tarea, tipo,
   subject, contraparte y adaptador persistidos. Sólo se ejecutan casos
   `medical_appointment` en `executing` o `waiting_external`.
2. La tarea debe estar `pending`, `running` o `waiting_external`, tener
   `attemptLimit > 0` y estar asignada a un adaptador registrado. Una tarea
   terminal no se vuelve a abrir.
3. Antes de un nuevo efecto, el ejecutor:
   - bloquea la tarea para asignar la próxima secuencia sin carreras;
   - bloquea el consentimiento exacto;
   - revalida autoridad mediante `ConsentManager`;
   - crea el `Attempt.started` y marca la tarea `running`;
   todo dentro de una transacción. Una revocación confirmada antes de crear el
   intento impide el efecto; una revocación posterior no borra un intento ya
   autorizado.
4. `idempotency_key` es único por tenant. El replay se resuelve antes de
   rechazar una tarea terminal o aplicar el límite. El mismo comando recupera
   el mismo intento: si es terminal, no reabre ni ejecuta; si está `started` o
   `waiting_external`, puede repetir la llamada con la misma clave sin
   reautorizar, porque la autoridad quedó reclamada al crear el intento.
   `Attempt.channel` guarda un fingerprint opaco del comando y adaptador, sin
   datos en claro, para detectar replay alterado aun después de reiniciar.
   Reutilizar la clave con cualquier cambio de comando o adaptador se rechaza
   sin ejecutar.
5. El adaptador se llama fuera de la transacción y siempre con la clave original.
   Un replay de un intento no terminal puede repetir la llamada porque el
   adaptador debe ser idempotente.
6. El resultado se persiste en una nueva transacción que bloquea intento y
   tarea, con compare-and-set desde `Attempt.started` o
   `Attempt.waiting_external`; un intento terminal nunca se sobrescribe. Ante
   una carrera se recarga y devuelve el estado ganador.
7. Mapeo de resultados:
   - `succeeded`: intento y tarea `completed`; evidencia sintética verificada se
     persiste como `Artifact.verified`. Una búsqueda pasa el caso a
     `needs_user`; una reserva conserva el caso ejecutándose para T014 y, si
     venía de `waiting_external`, vuelve a `executing`.
   - `waiting_external`: intento, tarea y caso quedan `waiting_external`.
   - `failed` reintentable con cupo: intento `failed`, tarea `pending`,
     `retry_scheduled` y el caso conserva su estado ejecutable.
   - `failed` reintentable sin cupo: intento/tarea `failed`, conserva
     `failure_code` y `retryable` originales, agrega handoff
     `ATTEMPTS_EXHAUSTED` y pasa el caso a `needs_human`.
   - `needs_user`: intento `failed`, tarea `pending` y caso `needs_user`.
   - `needs_human`: intento/tarea `failed` y caso `needs_human`.
   - fallo no reintentable: `NO_AVAILABILITY`, `INVALID_REQUEST` o
     `CONSENT_INVALID` derivan a `needs_user`; los demás a `needs_human`.
8. El límite usa filas persistidas y `max(sequence) + 1`, no llamadas ni
   contadores en memoria. Alcanzado el límite, una nueva clave no crea intento,
   no llama al adaptador y devuelve un outcome de handoff sin intento ni
   `AdapterResult`, siempre que no exista un intento en vuelo. Si la tarea está
   `running` o `waiting_external` con otra clave no terminal, se rechaza
   `TASK_IN_PROGRESS`; nunca se deriva ni se pisa el resultado en vuelo.
9. Toda consulta y escritura incluye `tenantId`. Cross-tenant se informa como
   no encontrado y nunca ejecuta el adaptador.
10. El ejecutor no completa casos, no crea calendario, no interpreta texto libre
    y no registra nombres, documentos, fechas de nacimiento ni texto clínico.
11. Para persistir evidencia, el registry exige un adaptador que además pueda
    obtenerla y verificar su checksum. Cada referencia debe tener el tipo
    esperado para la tarea y su `Artifact` se crea o recupera idempotentemente;
    un conflicto exacto se rechaza.

## Escenarios obligatorios

```gherkin
Scenario: ejecución exitosa autorizada
  Given un caso executing, tarea pending y consentimiento vigente
  When se ejecuta un TaskCommand válido
  Then existe un único Attempt.succeeded y la tarea queda completed

Scenario: doble submit idempotente
  Given una ejecución persistida para una idempotency key
  When se repite el mismo comando
  Then se reutiliza el intento y no se duplica el efecto ni la evidencia

Scenario: consentimiento revocado
  Given que el consentimiento fue revocado antes de reclamar el intento
  When se ejecuta el comando
  Then no se crea Attempt y no se llama al adaptador

Scenario: fallo reintentable
  Given cupo restante
  When el adaptador falla con retryable true
  Then el intento queda failed y se programa un nuevo intento

Scenario: intentos agotados
  Given que el límite de la tarea ya fue alcanzado
  When llega una nueva ejecución
  Then no se llama al adaptador y el caso se deriva a needs_human

Scenario: waiting external
  Given una respuesta externa pendiente
  When el adaptador devuelve waiting_external
  Then intento, tarea y caso conservan estado reanudable

Scenario: aislamiento
  Given una tarea del tenant A
  When tenant B intenta ejecutarla
  Then recibe no encontrado y el adaptador no es llamado
```
